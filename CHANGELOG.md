## [Unreleased]

### Fixed
- **Phase 3 manual Test Unit 1: defensive `event.isTrusted` gate on Activity Bar `@click` handlers** (`src/renderer/components/activity-bar.ts`). During manual testing, the `salary-history` extension was observed activating at startup before any deliberate user click. Diagnostic instrumentation (added and then reverted per the plan constraint) showed the activation flowed through Lit 3.3.3's bundled event-part `handleEvent`, which means a real DOM click event was firing on the `P` button. Since `isTrusted` was `true` on the offending event (real user click, most plausibly the window-focus click that happens to land on the Activity Bar), the activation is the **correct** response to a real click. The `event.isTrusted` gate (`@click="${(e: MouseEvent) => { if (e.isTrusted) this._selectView(view.id); }}"`) is now in place to rule out **synthetic** clicks (`element.click()`, `dispatchEvent(new MouseEvent('click'))`) — a defensive measure for future code paths. Phase 3 ships the current behaviour; the plan's Test Unit 1 expected-result text is updated to document the window-focus-click activation as correct, with a Phase 8 follow-up for a `window`-level pointer/keyboard engagement precondition so a window-focus click that lands on the Activity Bar does not spuriously activate an extension. No change to host, IPC, or registry code.
- **Phase 3: idempotency guard on the renderer's `view-changed` window listener** (`src/renderer/index.ts`). Repeated `extensions:activate-view` IPC calls for the same view (e.g. rapid double-click on the same Activity Bar button, repeated `_selectView` calls from a Lit re-render cycle) are now suppressed. Implementation tracks `lastDispatchedView` at module scope and returns early when the dispatched view matches the previous one. The Activity Bar's own `activeView` state still updates so the UI remains in sync. The host's `if (ext.moduleUrl) return true` short-circuit in `activateExtension` was the load-bearing guard for correctness; this renderer-side guard eliminates redundant IPC traffic and the corresponding `[host] msg received ... extension.activate` log lines. **REVERTED in commit `122e06a`** (see Test Unit 5 entry below) because the guard incorrectly blocked the legitimate re-spawn case.
- **Phase 3 Test Unit 4: Extension Host stdout mirrored to Renderer DevTools console** (`src/extension-host/host.ts`, `src/main/services/extension-ipc.ts`, `src/main/main.ts`, `src/preload/preload.ts`, `src/renderer/index.ts`, `src/types/finance-shell.d.ts`). Test Unit 4 expected the extension's handler output (e.g. `[salary-history] Pay History view requested`) to appear in the Renderer DevTools console, but extension logs only landed in the main-process terminal because the Extension Host runs as a separate `utilityProcess` child whose stdout is inherited by Main. **Why `stdio: 'pipe'` was not viable:** Electron's `UtilityProcess` does not expose `stdout` as a readable stream (only `spawn` / `exit` / `message` events), so Main cannot tail the child's stdout. The chosen mechanism: wrap `console.log` / `console.error` / `console.warn` in `host.ts` to also `postMessage` a JSON-RPC `host.log` notification (with stringified args for safe cross-process serialization). `extension-ipc.ts` adds a typed `HostLogEntry` and `onHostLog(listener)` API; `main.ts` subscribes and forwards via the new `extensions:host-log` IPC channel; `preload.ts` exposes `extensions.onHostLog(callback)` on the `contextBridge`; `renderer/index.ts` subscribes at the top level (before `DOMContentLoaded`) and dispatches to `console[level](...)` with a `[host log]` prefix. Each log line is preserved through Main's terminal (the wrapper keeps the original `console.*` call) AND now also reaches DevTools. **Verified by manual testing.** Plan's Test Unit 4 expected-result text updated to reflect that handler output is visible in DevTools.
- **Phase 3: operational telemetry — one `[extension-ipc] host spawned, pid=…` line per Host spawn** (`src/main/services/extension-ipc.ts`). During Issue 2 investigation (user reported multiple Extension Host processes in Task Manager across P→S→P click sequences), a one-line `console.log` was added inside `utilityProcess.fork`'s start path so manual testers can verify in the main-process terminal whether a new Host is spawned per click. The initial implementation logged immediately after `fork()`, but Electron populates `UtilityProcess.pid` asynchronously — `pid` is `undefined` until the `'spawn'` event fires. The fix: moved the log into a `this.process.once('spawn', …)` handler so `this.process.pid` is populated by then. **Verification:** across repeated P/S/P click sequences in a single session, only one `[extension-ipc] host spawned, pid=<N>` line appears in the terminal (the user's PID was 12244). The accumulated Hosts the user saw earlier in Task Manager were leftover from previous test runs (before the idempotency guard existed); the current code reuses the Host correctly.
- **Phase 3 Test Unit 3: Navigation Panel view-id mapping for extension views** (`src/renderer/components/navigation-panel.ts`). Test Unit 3 expects the Navigation Panel's view context to update when an Activity Bar button is clicked, but clicking the `P` button left the sidebar showing the generic "App Preferences / Manage Extensions" items instead of the Salary items. Root cause: the Activity Bar dispatches `view-changed.detail.view = 'salary-history'` (the manifest's view `id`), but `NavigationPanel.render()` checks `_currentView === 'Salary'` (the view's display `name`). The id and name never match, so the render falls through to the `else` branch. **Fix:** added a private static `_VIEW_CONTEXT_MAP: Record<string, string>` in `navigation-panel.ts` mapping `'salary-history' → 'Salary'` and `'__settings__' → 'Settings'`; `setView()` now translates via the map before storing. This is the minimum change to make Phase 3's hardcoded render branches recognise extension view ids. **Proper fix deferred:** the data-driven NavigationProvider pattern that consumes per-view contribution metadata is deferred to **Phase 5** per Self-Review §7; this map is the Phase 3 stop-gap. **Verified by manual testing** — clicking `P` now updates the Explorer panel to show "Salary" with "Pay History" and "Deductions" items; clicking `S` shows "Settings" with "App Preferences" and "Manage Extensions".

### Added
- **Phase 3 Test Unit 7: Extension loader skip warning routed to stdout (not stderr)** (`src/main/main.ts`). Test Unit 7 (`Invalid Manifest Is Skipped Gracefully`) requires that the loader's `[extensions] skipped "...: invalid manifest: ..."` warning be observable by the manual tester. The warning was emitted via `console.warn` (stderr), but several common Windows terminal configurations (notably PowerShell and certain VS Code-integrated terminals) do not surface stderr alongside stdout. The fix is one line: switch to `console.log` so the message lands on stdout and is visible in every terminal configuration. Verified by manual test — the skip warning now appears in the terminal where previously it was silent. The Plan's Test Unit 7 step 3 example output ("`[extensions] skipped ".../extensions/broken": invalid manifest: <error details>`") is satisfied with this fix.
- **Phase 3 Test Unit 6: 9 new unit tests covering the hot-disable contract for `ExtensionRegistry`** (`tests/unit/services/extension-registry.test.ts`). Test Unit 6 (`Disabling an Extension Removes Its Contributions`) verifies the hot-disable behavioural contract per `[Review fix §5.3]` (items 2/3/6). The contract was previously documented in the JSDoc but only `list()` was directly exercised by a unit test. New tests pin the registry half of the contract so future refactors cannot silently regress the gating:
  - `views()` excludes disabled extensions (item 2).
  - `commands()` excludes disabled extensions (item 2).
  - `views()` returns `{ extensionId, view }` shape with manifest view fields populated (the shape consumed by the `extensions:list` IPC handler).
  - `commands()` returns `{ extensionId, command }` shape with manifest command fields populated (same).
  - `views().find(...)` returns `undefined` for a disabled view id (item 3 — the gating that makes `extensions:activate-view` return `{ activated: false, reason: 'view not found' }` even when the Activity Bar has a stale button).
  - `commands().find(...)` returns `undefined` for a disabled command id (parallels the activate-view gating for the command-execution path).
  - `get(id)` returns the cached manifest for an enabled extension.
  - `get(id)` returns `undefined` for an unknown extension id.
  - `get(id)` still returns the cached manifest when the extension is disabled (item 6 — the design intent that the Host retains the activation so `executeCommand` continues to succeed after disable).

  Test totals: `extension-registry.test.ts` 8 → 17 tests; project total 56 → 65 unit tests pass. typecheck and lint both exit 0. The host-side guarantee that `executeCommand` still succeeds after disable (item 6) is exercised end-to-end by manual Test Unit 6 step 7 and by the existing `extensions:execute-command` IPC handler — this change just adds regression coverage on the registry half.
